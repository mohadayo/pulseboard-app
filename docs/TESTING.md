# テスト戦略（`docs/TESTING.md`）

PulseBoard は **Python API (`api-gateway`) / Go ワーカー (`metrics-worker`) / TypeScript BFF (`dashboard-bff`)** の 3 サービスで構成されています。各スタックで採用しているテストフレームワークや配置規約が異なるため、本ドキュメントに「どこにどの粒度のテストを書き、どう回すか」を集約します。

> **本ドキュメントの位置付け**
>
> - 方針の合意形成が目的であり、既存テストの追加・修正や CI 設定変更は含みません。
> - 実行コマンドの正解は最終的に `.github/workflows/ci.yml` と各サービスの `Makefile` / スクリプトです。乖離を見つけた場合は本ドキュメント側を更新してください。

## 1. 全体像

PulseBoard のテストピラミッドは以下の重み付けを想定します。

| 階層         | 主戦場                | 割合の目安 | 期待する粒度                       |
| ------------ | --------------------- | ---------- | ---------------------------------- |
| ユニット     | 各サービス内部         | 大        | 純粋関数・小さなクラス単位          |
| 統合         | サービス内 HTTP 層     | 中        | ルータ / ハンドラ / DB モックまで   |
| E2E          | `docker-compose` 全体 | 小        | ダッシュボードから見た主要導線のみ |

「速いテストを厚く、遅いテストを薄く」を基本とし、E2E は主要な happy path と回帰の要となるパスに絞り込みます。

## 2. サービス別テスト

### 2.1 `api-gateway` (Python 3.12)

- **フレームワーク**: `pytest`
- **ローカル実行**:

  ```bash
  cd services/api-gateway
  python -m pytest
  ```

- **推奨オプション**:
  - `-q` : サマリ表示で騒がしいログを抑制
  - `-k "<expr>"` : テスト名の部分一致で対象を絞る
  - `--maxfail=1` : 最初の失敗で打ち切り、ローカルでのフィードバックを短縮
- **HTTP 層のテスト**: FastAPI のテストクライアント (`TestClient` / `httpx.AsyncClient`) を使い、ルータレベルで検証します。外部呼び出しはモック化します。
- **注意点**:
  - `metrics-worker` への HTTP 呼び出しは必ずモック化し、テストが Go サービスに依存しないようにします。
  - 集約統計量の期待値は [`docs/METRICS.md`](./METRICS.md) の定義式に沿って手計算・固定値で書き、実装からの循環参照を避けます。

### 2.2 `metrics-worker` (Go 1.22)

- **フレームワーク**: 標準 `testing` パッケージ（テーブル駆動テスト）
- **ローカル実行**:

  ```bash
  cd services/metrics-worker
  go test ./...
  ```

- **推奨オプション**:
  - `-race` : データ競合検出。並行処理を含む集約ロジックでは必ず有効化。
  - `-run '^TestXxx$'` : 特定のテストのみ実行
  - `-count=1` : キャッシュを無効化して再実行
  - `-cover` : カバレッジをテキストで確認（`-coverprofile=coverage.out` で HTML 化可能）
- **テーブル駆動**: `cases := []struct{ name string; in ...; want ...; wantErr bool }` の形を基本とし、`t.Run(tc.name, func(t *testing.T) { ... })` でサブテスト化します。
- **注意点**:
  - 浮動小数点比較は等値比較を避け、絶対誤差 / 相対誤差の許容量を明示します。
  - 縮退ケース（要素数 0 / 1、定数入力、NaN / Inf）は [`docs/METRICS.md`](./METRICS.md) の挙動に沿った回帰テストを必ず 1 本入れます。

### 2.3 `dashboard-bff` (TypeScript / Node 20)

- **フレームワーク**: `services/dashboard-bff/package.json` の `scripts.test` に従います（Jest / Vitest 系のいずれか）。
- **ローカル実行**:

  ```bash
  cd services/dashboard-bff
  npm ci
  npm test
  ```

- **推奨パターン**:
  - **純粋関数のユニットテスト**を最も厚く配置します（例: パーセンタイル計算、パラメータパース）。
  - **HTTP ハンドラ**は `supertest` 等でルータレベルの入出力を検証し、下流 API はモック化します。
- **注意点**:
  - `api-gateway` への HTTP クライアントは必ずモック化します（`nock` / `msw` / `jest.mock` のいずれか）。
  - 統計値の期待値は Python/Go 側と一致させ、[`docs/METRICS.md`](./METRICS.md) の定義に沿って固定値で書きます。

## 3. テスト階層と粒度

- **ユニット**: 副作用のない純粋関数・小さなクラスを直接呼び出して検証します。ここが厚いほど回帰検知が速くなります。
- **統合（サービス内）**: HTTP ルータやハンドラを起点に、DB / キャッシュ / 外部 API はモック化して検証します。1 サービス内で完結させ、他サービスは呼びません。
- **E2E**: `docker-compose` で 3 サービスを立ち上げ、ダッシュボード視点の主要導線を確認します。E2E は数を増やさず、代表的な happy path と回帰の要にとどめます。
- **契約テスト（任意）**: サービス間 IF が変わる際は、モックが「実装のふり」を続けないよう、実サービスに対するスモークテストを 1 本ずつ用意することを推奨します。

## 4. CI との対応関係

- CI 定義は `.github/workflows/ci.yml` を単一の情報源とします。
- 各サービスのローカル実行コマンドは、CI 内で実行されるコマンドと同じであるべきです。乖離を見つけた場合は、まずローカル側 / ドキュメント側を CI に合わせて調整します。
- Makefile には全サービスの lint / test を横断で回すターゲットが用意されています。詳細はリポジトリルートの `Makefile` を参照してください。

## 5. テストコードの配置規約と命名

| サービス            | 配置                                | 命名                          |
| ------------------- | ----------------------------------- | ----------------------------- |
| `api-gateway`       | `services/api-gateway/tests/`       | `test_*.py`                   |
| `metrics-worker`    | 実装ファイルと同ディレクトリ         | `*_test.go`                   |
| `dashboard-bff`     | 実装ファイル近傍 or `__tests__/`    | `*.test.ts` / `*.spec.ts`     |

- Python は `tests/` 配下に集約し、`pytest` のディスカバリに任せます。
- Go は言語仕様に従い、対象ファイルと同ディレクトリに `*_test.go` を配置します。
- TypeScript はコロケーション（対象ファイル近傍）を基本とし、大きく育つ場合のみ `__tests__/` にまとめます。

## 6. カバレッジの運用方針

- **強制はしません**（PR ゲートとしての最低ライン閾値は現時点で設けません）。
- **可視化は歓迎**します。ローカルで確認する場合の例:
  - Python: `python -m pytest --cov`
  - Go: `go test ./... -cover`
  - TypeScript: `npm test -- --coverage`
- カバレッジ数字を「絶対的な品質」と見なさず、**「テストを書き忘れた分岐がないか」を発見する道具**として扱います。
- 重要なドメインロジック（[`docs/METRICS.md`](./METRICS.md) の統計量計算、外れ値判定、パーセンタイル計算など）はカバレッジよりも **境界値ケースの網羅**を優先します。

## 7. 新規テスト追加時のチェックリスト

新しくテストを追加・修正する際は、以下を確認してください。

- [ ] 対象コードは **どの階層**（ユニット / 統合 / E2E）に属するか意識できているか
- [ ] 該当サービスの **既存の配置規約 / 命名規則** に従っているか
- [ ] **外部サービスや外部 I/O はモック化**されており、他サービスの起動に依存していないか
- [ ] 統計量の期待値は [`docs/METRICS.md`](./METRICS.md) の定義に沿った固定値か
- [ ] 浮動小数点比較で **許容誤差**が適切に設定されているか
- [ ] 縮退ケース（空入力・単一要素・定数・NaN / Inf・タイムアウト）に **回帰テストが 1 本以上**あるか
- [ ] CI と同じコマンド (`pytest` / `go test ./...` / `npm test`) で **ローカルでも通る**か
- [ ] テスト名は「何を保証しているか」が読めば分かる粒度か
