## 1. 起動 / 停止 / 再起動

### ローカル環境

```bash
# 起動 (依存サービス含む)
docker compose up -d

# 状態確認
docker compose ps

# 停止 (コンテナは残す)
docker compose stop

# 停止 + コンテナ削除
docker compose down

# 個別サービスの再起動
docker compose restart <service-name>
```

### 起動順序に依存があるとき

`services/` 以下の各サービスは `depends_on` で暗黙的な起動順を持つ。手動で順序を制御したい場合は `docker compose up -d <service-a>` の後で `docker compose up -d <service-b>` と段階的に立ち上げる。

## 2. ヘルスチェックの確認

すべてのサービスは `GET /healthz` を最低限備える。

```bash
# サービス個別に確認
curl -sf http://localhost:${PORT}/healthz | jq .

# 全サービス横断で確認 (Makefile ターゲットを推奨)
make health
```

`/healthz` は依存 (DB, キャッシュ) を含めた活性性を返す。`/livez` は自プロセスの生存のみを返し軽量なので、外形監視には `/livez` を使う。

## 3. ログとメトリクスの入り口

- **ログ**: `docker compose logs -f --tail=100 <service>` で追跡する。JSON 行なので `jq` で絞り込みできる。
- **メトリクス**: 各サービスは `/metrics` (Prometheus 形式) を公開する。
- **相関 ID**: すべてのログ行は `request_id` を持つ。障害の追跡はまず影響ユーザーの `request_id` から始める。

```bash
# 特定 request_id のログのみ抽出
docker compose logs <service> | jq 'select(.request_id == "REQ-ABC123")'
```

## 4. デプロイ

### 事前チェック

1. `main` ブランチが CI グリーンであること
2. マイグレーションが必要な変更がある場合、DDL を先に流す (下位互換を保つ)
3. `CHANGELOG.md` に対象バージョンのエントリがあること

### 手順

```bash
# タグを打つ
git tag -a v0.X.Y -m "..."
git push origin v0.X.Y

# デプロイ (環境ごとの手順は各環境の README を参照)
make deploy ENV=<staging|production>
```

### デプロイ後の確認

- ヘルスチェック (§2) が全サービスで OK
- エラー率 / P95 レイテンシが変動していない
- 主要ユーザーフロー 1 系統を手動で通す

## 5. ロールバック

原則、"直前のグリーンなバージョンにイメージタグを戻して再デプロイ" が最速で確実。

```bash
# 直前タグを確認
git tag --sort=-committerdate | head -5

# 直前タグでデプロイ
make deploy ENV=production TAG=v0.X.Y-1
```

DB マイグレーションが絡む変更のロールバックは、下位互換が保たれているかを確認する。互換性が壊れる場合は "前方回復" (バグ修正の追加デプロイ) を選ぶ。

## 6. インシデント一次対応

深刻度は影響の広さで判定する。判断に迷ったら "高いほう" を選ぶ。

| 深刻度 | 判断基準 | 対応 |
| :-- | :-- | :-- |
| Sev-1 | 全ユーザー影響 or データロス懸念 | 即座にオンコール招集、状況共有チャンネル作成 |
| Sev-2 | 一部ユーザー影響 or 主要機能劣化 | 30 分以内に着手、Slack で共有 |
| Sev-3 | 単発エラー・軽微な劣化 | 翌営業日中に対応 |

### 一次対応フロー

1. **止血 (Mitigate)**: 影響を止める。ロールバック (§5)、機能フラグ OFF、レートリミット引き下げ、など。
2. **観測 (Observe)**: ゴールデンシグナル (レイテンシ / トラフィック / エラー / サチュレーション) をダッシュボードで確認。
3. **記録 (Log)**: Slack のインシデント専用スレッドに、開始時刻・現象・対応した内容を時系列で残す。
4. **共有 (Communicate)**: Sev-1 / Sev-2 はステークホルダーに定期共有する (30 分ごと)。
5. **収束 (Resolve)**: 影響が収束したら宣言し、ポストモーテムのオーナーを決める。
